## 2. Benchmark 的核心定义

ReviewBench-Maintainability 评测模型是否能针对真实 code review concern 做出
行为保持、聚焦、实质的代码质量提升。

每道最终题必须满足四层要求：

1. 真实 GitHub merged PR 和真实 reviewer comment。
2. 双模型严格判断 reference fix 是实质维护性提升。
3. start 与 source-only golden 通过同一 correctness Oracle。
4. Oracle 必须稳定、非空并覆盖 changed-old production line。

它与普通 bug-fix benchmark 的区别是：

- 主要目标是 maintainability，而不是修复功能错误。
- start 和 golden 的公开行为通常应保持一致。
- target tests 不能用于绑定作者的具体实现。
- correctness 是回归安全网，维护性 judge 才是主要质量信号。
- 任务不能靠检查私有 helper、签名、源码结构、AST、MRO 或调用次数判分。

## 3. 严格质量门

当前质量 schema：

```text
reviewbench-quality-improvement/v1
```

每个候选必须由 GPT-5.6 Sol 和 Claude Opus 4.8 两个不同模型一致严格通过。

通过条件：

- 原代码存在明确 code smell。
- reference fix 与 reviewer concern 可归因。
- reference fix 有实质质量改善。
- primary kind 是 maintainability。
- primary goal 不是 behavior change。
- 非纯 style、注释、机械 rename 或 easy cleanup。
- quality score 至少 4/5。
- confidence 至少 0.8。
- intrinsic difficulty 为 medium 或 hard。
- 不接受 partial。
- 不引入同等严重的新维护债。

Difficulty 采用保守规则：

- 两个质量模型都判 hard，发布难度才是 hard。
- 其他通过题发布为 medium。

## 6. Oracle 的严格要求

每个发布题必须具备：

- 精确 `start_sha`。
- review-local、source-only golden。
- 不注入 target tests。
- start 3 次稳定运行。
- golden 3 次稳定运行。
- 非空 PASS_TO_PASS。
- 公开或可观察行为断言。
- changed-old production line coverage。
- 相同 Oracle 可用于所有模型候选。
- 不检查作者私有实现细节。

允许的 session behavior tests：

- 必须 import、link 或执行真实 production code。
- 可以 stub 外部 I/O、RPC、数据库和系统边界。
- 不能复制生产逻辑后测试复制品。
- 不能用 `#line`、假 probe 或 toy implementation 伪造 production coverage。

允许的结构性拒绝：

- reviewer anchor 是 test/QA infrastructure，没有 production changed-old line。
- source-only golden 发生真实公开行为变化。
- changed-old anchor 没有 executable production line。
- 必须依赖不可获得的专有 SDK、商业程序集、私有 artifact 或 license。
- 任务局部 golden 无法在 start base 上形成合理 dependency closure。

不允许直接拒绝的情况：

- 没有现成测试。
- 环境首次安装失败。
- 现有测试没有覆盖 changed line。
- start 和 golden 行为相同。
- 需要编写 session behavior test。

## 7. 关键审计修正

### 7.1 初版 Native 35 道整体作废

独立 Oracle 审计发现初版 Native harness：

- 只编译 `oracle_main.cpp + production_focus.cpp`。
- `production_focus.cpp` 是手写 toy reimplementation。
- 使用 `#line` 将 trivial probe 伪装为真实 production file/line。
- start 和 golden 因测试复制品不变而得到 vacuous P2P。

该批 35 条全部撤销发布资格并归档到 invalid artifacts。

Native 随后从零重做：

- checkout 真实 start 和 source-only golden。
- 编译或实例化真实 repository source/header。
- harness 调用真实 production symbols。
- gcov/llvm-cov 来自真实 translation unit。
- start/golden 各 3 次。

最终：

- 33 PASS_TO_PASS。
- 2 STRUCTURAL_REJECT。

第二个独立 reviewer 对 33 道最终 pass 做了系统和逐题 anti-fraud 审计，没有发现
阻塞问题。

### 7.2 Other 线 stub 审计

Other 线初版有 `.behavior.inc` 抽取和 helper stub 风险。复审后：

- DistributedProofreaders 和 HMRC 改为真实 production module。
- Nix 和 OpenProject 的真实 Oracle 保留。
- Pupilfirst 和 GitHub Actions YAML 因没有真实 changed-old production
  coverage 撤销。
- Microsoft STL 因 MSVC 和 Windows SDK 不可获得而 blocked。

最终 4/7 通过。

### 7.3 “无行为差异”错误拒绝

多条语言线最初把 start/golden 行为相同当作 structural reject。该口径已纠正。
维护性重构本来就应行为保持，Oracle 的目标是：

AND stable start/golden
AND non-empty P2P
AND changed-old production coverage

- GPT-5.5：184 → 198。
- Claude Opus 4.8：180 → 187。

Gemini 的主要损失发生在多轮 agent loop generation。它有时输出整段
`assistant_action/tool_result` continuation，协议层经过两次修正：

1. 多对象响应不能取第一个历史 action，应按文本顺序识别最后有效 action。
2. worktree 尚无改动且响应同时包含 `edit → finish` 时，不能只取空 finish，
   应优先执行 edit。

明确打满 16K reasoning/output budget 的任务允许使用 32K 技术恢复。API timeout
和 agent loop failure 均单独记录，不冒充 Git patch apply failure。
