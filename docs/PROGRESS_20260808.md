- 后续瞬时失败不能撤销已经完成的 3x start、3x golden、P2P 和 coverage；
- 覆盖旧记录必须提供更强证据，而不是仅凭一次环境失败；
- 所有发布 Oracle 仍逐题满足严格门。

### 3.1 策展结果

Rust 的 `recoverable_pending_curation` 需要逐题编写只走公开 API 的行为测试。
首批 18 道中 15 道转为 strict pass，证明主要瓶颈是 Oracle 策展而不是任务
无效。有效模式包括：

- CLI 通过真实二进制入口触发参数解析；
- FRAME pallet 用最小 mock runtime 走公开 dispatchable；
- 科学计算库用基无关的物理量或特征值验证行为；
- crate 级 integration test 命中重构前 OLD 行；
- `source_expansions` 补全 source-only golden 中漏掉的同一生产变更闭包。

结构性拒绝包括：

- 关键模块或类型只在 private / `pub(super)` 路径可达；
- target 删除了被测公开功能，无法构造两侧都编译的行为测试；
- binary-only crate 没有公开 library API；
- Rust 只是 C/CMake 主程序的 staticlib FFI 组件；
- 需要不可再分发 SDK 或专有硬件工具链；
- 变更行只包含声明，或宏展开后的 span 无法映射回真实 OLD 行。

### 3.2 Native 审计

Native 任务继续遵守 20260728 审计后的规则：

- 禁止 toy reimplementation；
- 禁止 `#line` coverage probe；
- 必须编译或实例化真实 repository production code；
- 必须调用真实公开或可观察入口；
- gcov/llvm-cov 必须来自真实 translation unit。

依赖缓存恢复额外救回 AutoPas、LAPIS-SILO、NumeRe 和
kokkos-execution-space。BSMPT 复用已有 Conan 镜像和 warm cache，用公开
`ModelID::FChoose(...)->initModel(...)` 行为验证旋转约定重构，覆盖 124 条
changed-old line。

## 4. 三模型 Agentic 评测

协议：

```text
agentic-line-edit/v1
```

模型只能读取仓库文件，并编辑锚点 production file。模型不输出 diff；host
在隔离临时目录中应用 1-based line edit，最终由 Git 生成 patch。

维护性门使用 human-golden 校准后的 rubric v2：

- correctness 由 executable Oracle 负责；
- LLM judge 不再从 diff 猜测行为保持；
- 不因同文件相关伴随修改自动拒绝；
- 必须解决 review concern、质量至少 4/5，且不能引入同等严重的新债务。

## 5. 关键评测修正

### 5.1 Claude aggregate proxy 假失败

`wave-003` 首次使用 8787 aggregate proxy 生成 Claude 候选，得到
95 generated / 95 failed。失败形状与任务难度不一致。

同一批 95 个失败任务改用已验证的 4141 direct endpoint，从原始 source
fresh-run：

```text
94 generated / 1 genuine max-round failure
```

随后只对这 95 个 Claude task-model pair 重放 correctness；其他 475 条记录
保持 object-identical。更新后 wave-003 的 Claude 结果从 43/190 修正为
81/190。

该事件说明：

- endpoint failure 不能解释成模型能力；
- 已耗尽 32 轮的失败 trace 不能用普通 resume 重采样；
- terminal failure 需要 `--restart-failed` 或独立 fresh-run；
- 发布前必须比较 endpoint identity、输出形状和异常失败率。

同样的审计随后应用于 wave-001 的 21 个旧 Claude failure：

```text
19 generated
17 correctness pass
10 maintainability pass
9 Resolved
2 genuine generation failures
```

这 21 道以预先冻结 ID 的 correction overlay 发布，不改写原 wave。Claude
414-hard 总分因此从 168 修正为 177。

### 5.2 Judge 空响应

高并发 8787 judge 调用产生 110 个空 raw response，解析表现为
`invalid addressed value: ''`。降低并发并切换 4141 direct endpoint 后，
所有可生成候选均完成有效 rubric-v2 judgment。

空响应被视为 transport/judge error，而不是 maintainability reject。

### 5.3 Canonical correctness staging

correctness 工作目录会保留重跑前备份，例如
`csharp-before-exact-dependency-rerun.jsonl`。汇总器读取目录下所有 JSONL，
若直接指向工作目录会产生 duplicate task-model key。

正式汇总只读取 `correctness-canonical/`，其中恰好包含七个权威 lane 文件。

### 5.4 发布前 infrastructure-error audit

第一次 compact packaging 后，release gate 额外扫描 normalized status，发现：

- wave-001 有 4 条 `judge_error`；
- OpenAssetIO 两道任务、三个模型共 6 条 correctness 记录引用了错误层级的
  harness path，状态为 `retry infrastructure`；
- 已发布 Sniffy/Gemini 是 `generation_api_timeout`。

这些记录没有作为负分冻结：

1. 4 条 judgment 在 4141 direct endpoint 重试，全部得到合法 verdict；
2. OpenAssetIO 修正 harness materialization，6/6 candidate 真实 Oracle PASS；
3. Sniffy/Gemini fresh generation 成功，真实结果是 scope 737>400 且 Java
   编译失败，maintainability judge 通过，因此最终仍 unresolved，但原因已经从
   API timeout 变成真实 candidate failure。

修正后总榜从 Claude 167、Gemini 141 更新为 Claude 168、Gemini 143；
GPT 保持 212。`package_hard_release.py` 现在拒绝：

- 非 `generated`/`failed` 的 generation status；
- `judge_error` / `input_error`；
- correctness `retry infrastructure`；
- applied patch 缺少 final judgment。

## 8. 当前边界

1. Solver 仍只允许修改一个锚点 production file；自然多文件重构会被低估。
2. 统一 maintainability judge 仍是 Claude Opus 4.8，不能完全排除自裁偏差。
3. 414 hard 是严格可执行子集，不是所有真实 maintainability review 的随机样本。
4. 重型仓库更容易因历史工具链、依赖、服务和 build cost 被排除。
5. 新 374 hard 的 difficulty 合并口径与既有 40 hard 不完全相同，发布中已显式标注。
6. compact release 不附带原始 worktree 和容器镜像；完整 replay 仍需要恢复历史环境。
